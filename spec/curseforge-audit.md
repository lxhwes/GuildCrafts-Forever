# CurseForge comment audit

Player reports from comments on upstream GuildCrafts' CurseForge page (TBC Anniversary/Classic,
upstream versions 1.3–2.0.1, Mar–Sep 2026), checked against this fork. Started 2026-10-03
against `main` at `60c6b32`. Investigation only: nothing here has been fixed.

Statuses:
- **PRESENT**: the code shows the issue exists on Forever.
- **PARTIAL**: part of it exists, or it exists only under some conditions.
- **ABSENT**: the code shows it doesn't exist or was fixed.
- **NEEDS-INGAME**: only an in-game check can settle it. The entry gives the probe idea.
- **N/A-FOREVER**: can't happen on Forever. The entry says why.

Existing IDs refer to `spec/forever-plan.md` (H/F/C/Q), with the GitHub issue number where
one exists (#4–#39). Anything marked "unverified" is a guess that the code doesn't settle.
File paths under `GuildCrafts/` are given relative to that folder.
Line numbers are at commit `60c6b32`. Read them with `git show 60c6b32:<path>`, because
the shared working tree can carry other sessions' uncommitted edits.

Entry format: report summary | status | evidence | existing ID | suggested severity
(blocker/hardening/post-launch) | notes.

### `!gc` responder behavior

Line numbers are at `60c6b32`. `Core.lua` and `Modules/*` are under `GuildCrafts/`.

**The path, as the code runs it:**

1. **Trigger.** `CHAT_MSG_GUILD` calls `OnGuildChatMessage` (`Core.lua:73`, `:319`). The handler
   takes only `msg`, so it never knows who asked.
2. **Gates, in order.** A secret `msg` returns (`:322`). A line starting `[GuildCrafts]` records
   the echo time and returns (`:325-328`). `myRole == "NONE"` returns (`:331`). Anything that
   isn't `!gc <query>` returns (`:333-334`). An in-instance client returns (`:338-339`). Nothing
   in the path checks `SyncPausePolicy` or `C_RestrictedActions`.
3. **Query.** A shift-clicked `|Hitem:` or `|Henchant:` link becomes a recipe key (`:341-351`).
   Link markup is stripped (`:353-363`), then any leading `Word: ` prefix (`:365`).
4. **Cooldown.** Keyed on the lower-cased query text (`:369`), 30 s (`:228`, `:371`). Only the
   client that posted stamps it, and only after a match (`:447`). There is no per-asker
   cooldown, and a no-match reply never stamps.
5. **Choosing the responder.** `RecomputeElection` sorts the `addonUsers` keys: first is DR,
   second is BDR (`Comms.lua:292-312`). The reply delay depends on role:
   - DR with peers: 0–1.5 s, a float (`Core.lua:405`);
   - DR that knows only itself: 2–6 s, an integer (`:399`);
   - BDR: exactly 5 s (`:382`);
   - everyone else: 12–20 s, an integer (`:387`).
6. **Staying quiet.** It does both: every responder sets a timer and listens. When the timer
   fires, the client skips if a `[GuildCrafts]` guild line or a `GC_ACK` arrived after it
   scheduled (`:417-418`). The responder sends `GC_ACK` before posting (`:442`, `:451`).
   Receivers record it and add the sender to `addonUsers` (`Comms.lua:1510-1517`). `GC_ACK` goes
   through AceComm and ChatThrottleLib at `NORMAL` priority (`Comms.lua:1389`). The chat reply
   itself is a direct `SendChatMessage` (`Core.lua:468`).
7. **Reply size.** At most 3 results with 2 names each, plus a "+N more" line: 4 lines, 0.5 s
   apart (`:454-473`). Each line fits 255 bytes (`FormatCraftersLine`, `:236-276`). A no-match
   query posts the asker's text back to guild chat (`:440-444`).
8. **When the DR is paused, in an instance or restricted.**
   - `SyncPausePolicy` doesn't gate `!gc`. A DR in combat or a zone grace period still answers.
     `HEARTBEAT`, `HELLO` and `GC_ACK` bypass the pause (`Comms.lua:61-65`).
   - In an instance the DR stays silent (`Core.lua:338-339`). Its watchdog is kept fresh
     (`Comms.lua:449-456`), so it keeps believing it's DR.
   - Under `C_RestrictedActions` nothing is checked. If guild chat arrives as a secret value,
     the handler returns at `Core.lua:322`. That skips the query, and it also skips recording
     another responder's echo.

### Performance and lag from sync

Line numbers are at `60c6b32`. Reports: combat spikes up to about 2 s, spikes on raid nights
when many people log in at once, and lag in cities bad enough that most of the guild keeps the
addon disabled.

No frame time has been measured. The ranking below comes from reading the code: how much work
each hot spot does, multiplied by how often it fires. The measurements that would confirm it are
at the end of this section.
